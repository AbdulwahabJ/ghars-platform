MODE: Power

ADD SECURE PATIENT FILE ATTACHMENTS TO GHARS.

GOAL:

Allow authorized clinic users to upload images and documents to a patient's medical file:

1. During new patient creation.
2. Later from the existing Patient File.

This must be simple, professional, secure, tenant-isolated, and suitable for clinical use.

IMPORTANT:
Do NOT add a third Patient File tab.

The Patient File must remain exactly:

- بيانات المريض
- إجراءات المريض

Attachments must live inside:
بيانات المريض / Patient Information

Do NOT publish automatically.

10. SAFE PATIENT CREATION FLOW
==================================================

Because the Patient may not yet exist while files are selected:

implement safe temporary upload/staging.

Preferred flow:

temporary upload
→ patient successfully created
→ attachments linked transactionally to patient

If patient creation fails:
do NOT leave permanent orphan attachment records.

If user cancels:
temporary uploads should be safely cleaned up according to current storage policy.

Do not create broken attachments.

==================================================
16. TENANT ISOLATION
==================================================

CRITICAL.

Every attachment belongs to:

tenant_id
patient_id

Backend derives tenant from authenticated session.

Never trust frontend tenantId.

A user in Tenant A must NEVER:

- list
- preview
- download
- edit
- delete

attachments belonging to Tenant B.

==================================================
17. PRIVATE STORAGE
==================================================

CRITICAL:

Do NOT store patient medical files in:

- public static folders
- frontend assets
- local ephemeral filesystem
- publicly accessible URLs

Use the existing durable private object/file storage architecture.

If Ghars currently has no suitable durable private storage:
STOP and report this as a blocker instead of implementing unsafe local storage.

Database should store metadata/storage key, NOT large file blobs unless existing architecture explicitly uses that pattern.

==================================================
18. SECURE FILE DELIVERY
==================================================

Attachments must not have permanent public URLs.

Use authenticated access / short-lived signed URLs or equivalent secure mechanism.

Patient files contain medical information.

==================================================
19. MIME / EXTENSION VALIDATION
==================================================

Validate server-side:

- actual allowed MIME types
- extension
- size

Do not trust frontend validation only.

Reject unsupported content safely.

==================================================
20. SAFE FILE NAMES
==================================================

Never use raw user filename as filesystem/object-storage key.

Generate safe unique storage keys.

Preserve:

original_filename

only as metadata for display.
